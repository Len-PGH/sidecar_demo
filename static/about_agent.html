About the agent UI

This is the page a sales rep keeps open during every call. It connects to SignalWire on the rep's behalf, places outbound calls, listens to the AI copilot's coaching cues in real time, and surfaces the customer transcript as the conversation unfolds. No supervisor view, no historical reporting — just one rep, one call, one workspace.

What the rep sees

Four surfaces, stacked vertically with the action bar pinned at the bottom:

  • Coach — the most recent AI insight, displayed as a hero card. Older insights drop into the "Recent insights" list below it, capped at six. When no call is live the orb pulses gently to indicate the AI is idle.
  • Conversation — live transcript, customer bubbles in blue on the left, agent bubbles in red on the right. Identical turn/utterance content from overlapping events is deduped automatically.
  • Context — when the AI invokes lookup_competitor or get_account_status, the structured payload renders as a card here. Newest on top, capped at five.
  • Action bar — Connect / Go Online / Dial during setup; Mute / Hangup once a call is up. After a call ends, a "New call" banner replaces the controls — click it to clear the previous call's debris.

The call lifecycle

page load │ ▼ [ Connect button ] ── POST /sidecar/token ──▶ mint SAT + ws_ticket │ │ │ ▼ │ SignalWire SDK boots, registers │ ▼ [ Go Online ] (optional) ── client.online() ───▶ accepts inbound │ │ OR ▼ [ Dial ] ── client.dial(addr, { userVariables }) ────▶ SignalWire │ ▼ relay renders SWML from /sidecar executes ai_sidecar + connect verbs │ ▼ customer answers → call.status$ fires ▲ │ │ ▼ │ UI flips to "in call" │ │ │ ▼ │ ◄── /ws/events stream ─── insights, tools, transcribe events │ └── hangup / disconnect ─── _onCallEnded() flushes UI ◄──┘

The dance is split across three runtime actors:

  1. The SignalWire SDK in this page does the WebRTC. It needs a SAT (subscriber access token) which we mint via POST /sidecar/token on Connect. The same response carries a ws_ticket the page later uses to open the /ws/events WebSocket without HTTP Basic.
  2. The SignalWire relay runs the SWML script we return from /sidecar. It bridges the two legs (rep's browser ↔ customer PSTN), attaches the ai_sidecar verb on top, and starts firing events.
  3. The brian_sidecar backend hosts the SWML, handles the SWAIG tool callbacks, fans events out to every connected WS subscriber, and persists everything to the CDR.

How the Coach pane stays current

The AI emits two kinds of coaching:

  • Native insight events — the model literally fires an event with a raw text field. Rare in practice with gpt-4o-mini.
  • Tool-result prose — when the model calls lookup_competitor or log_objection, the tool's response field is itself a coaching cue ("Anchor on TCO, not seat cost. Mention the $79 vs $99 ACME framing."). The page extracts this and treats it as if it were an insight.

Both paths feed pushInsight(), which: 

function pushInsight(evt, ts) {
  els.coachText.textContent = evt.raw;
  els.coachTs.textContent   = evt._source
    ? `${ts} · ${evt._source}`   // synthesised: shows "from lookup_competitor"
    : ts;                         // native: just the timestamp
  // re-trigger the flash animation so a back-to-back insight pulses again
  els.coachCard.style.animation = "none";
  void els.coachCard.offsetWidth;
  els.coachCard.style.animation = "";
  // push the previous hero down into the "Recent insights" list, cap at 6
  els.coachList.insertBefore(li, els.coachList.firstChild);
  while (els.coachList.children.length > 6) els.coachList.lastChild.remove();
}

Two paths into the transcript

SignalWire's relay only sends some events to the backend webhook — others flow directly to the SDK on this page. To get both sides into one chronological transcript, the page has to act as a bridge:

  • The relay POSTs turn events to /sidecar/events with the customer's text. The backend fans these out via /ws/events, where this page picks them up.
  • The relay sends transcribe.utterance events directly to the SDK on this page (the agent's side). This page picks them out of the SDK's event stream AND posts them back to /sidecar/speaker-event so the backend can broadcast them to the supervisor monitor.

There's a feedback-loop risk: the backend's broadcast comes back through /ws/events, which this page subscribes to. Without a guard the page would re-POST every echo and the loop would never stop. Synthetic broadcasts carry origin: "monitor_relay"; the re-POST is short-circuited when that marker is present.

Mute is just a track flip

What used to happen: the mute button called call.self.mute(), which (per the SDK) tears down the local mic device, then unmute() re-acquires it via getUserMedia + ICE renegotiation. Result: a ~5 second gap between clicking unmute and the customer hearing audio.

What it does now: flip track.enabled on every local audio track. This is the standard WebRTC mute pattern — the track stays in the peer connection, audio is just silenced at the source. Instant in both directions, no renegotiation cost. 

function toggleMute() {
  const want = !state.muted;
  for (const t of state.call.localStream.getAudioTracks()) {
    t.enabled = !want;
  }
  state.muted = want;
  _renderMuteIcon(want);
}

Side effect: the server-side participant state doesn't reflect "muted", because we never tell the relay. Nothing in this app surfaces that, so the trade-off is one-sided. If a supervisor monitor ever needs to render a muted indicator we can add a low-priority background call.self.mute() after the track flip — UI stays instant, server learns within a second.

End-of-call cleanup

The SDK's call.status$ observable doesn't always emit a terminal status reliably — sometimes disconnecting fires and nothing follows, sometimes the call object goes straight to destroyed, sometimes neither comes through and only the destroy event remains. To keep the chip from getting stuck on "call connected" the page subscribes to all three signals: 

// status$ stream — covers the usual transitions
call.status$.subscribe(s => {
  if (s === "disconnecting" || s === "disconnected"
      || s === "destroyed"  || s === "ended") {
    _onCallEnded();
  }
});

// destroy event — backstop when status$ never delivers a terminal value
call.once?.("destroy", _onCallEnded);

// Plus a forced flush right after the user clicks hangup, in case
// neither of the above fires before the request settles.
async function hangup() {
  await state.call.hangup().catch(...);
  _onCallEnded();
}

_onCallEnded() is idempotent — every path can fire it unconditionally, the UI flush runs every time (so a stale state always gets cleared), and the subscription teardown only happens once (guarded by a flag that resets in attachCall).

Self-heal on SDK timeouts

SignalWire's subscriber state can wedge — sometimes the relay holds onto an old subscriber identity and refuses new tokens, returning RPCTimeoutError on register or CallCreateError on dial. When that happens the page calls DELETE /sidecar/subscriber, which evicts the cached identity on the SignalWire side, then reloads. The next /token mints a fresh one and the page is back online without manual intervention.

Where the boundaries are

  • One rep per page. No multi-call queueing, no roster, no presence handoffs. If you want supervisor visibility across many reps, that's the Live calls monitor.
  • SAT scope is tight. The minted token is scoped to one specific Fabric address (the sidecar resource), valid for 24 h. If you want the rep's same browser to dial elsewhere they need a different SAT.
  • Transcript display is best-effort. The bubbles render whatever the SDK delivers, deduped against the backend fanout. If the SDK drops a frame the transcript has a gap — the CDR's persisted copy fills it in post-call.
  • Recording happens at the relay, playback at the CDR. When SIDECAR_RECORD_CALLS=1 the rendered SWML carries a record_call verb (stereo mp3, both directions) so SignalWire saves the bridged call to its cloud recording store. The agent surface still just plays live remote audio — playback of past calls lives in the CDR detail modal. Retrieval uses SignalWire's LaML-compat recordings endpoint (/api/laml/.../Recordings.json?CallSid=…) because it's the only path that supports filtering by call ID — the native /api/relay/rest/recordings list endpoint exists but silently ignores every filter we tried (call_id, CallSid, relay_pstn_leg_id), so finding "the recording for this one call" requires a one-shot LaML query rather than client-side filtering of every recording in the project.
