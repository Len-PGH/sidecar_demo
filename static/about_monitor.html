How the live monitor works

A supervisor opens one page and sees every active sales call in the system — who is speaking, what they just said, what coaching the AI is whispering to the rep, and a "listen in" button that pipes the live audio into the browser. This is how the data flows from a PSTN call leg all the way to a DOM cell that pulses every time a word comes through.

What you see

The monitor is a single table, refreshed three ways:

  • A 3-second poll against /sidecar/active-calls rebuilds the row set from authoritative state.
  • A push WebSocket at /sidecar/ws/events patches individual cells the instant a transcribe, insight, or tool-call event arrives — sub-second latency without thrashing the table.
  • An audio WebSocket at /sidecar/ws/audio/listen streams μ-law PCMU frames from one specific call, which the browser decodes and plays through an AudioWorklet.

Each row has cells for customer said, rep said, and coaching. They flash bright when fresh (under four seconds old) and fade to a quieter style after that, so a supervisor can glance at the table and see who has talked most recently without reading every word.

The data path, end to end

PSTN caller browser (rep) browser (supervisor) │ ▲ ▲ ▼ │ │ SignalWire Relay ─── transcribe.* ────► SignalWire SDK ─┐ │ │ │ POST │ │ /events webhook (turn, insight, tool_*) ▼ /speaker-event │ ▼ ┌─────────────┐ │ brian_sidecar (FastAPI) ◄──────────────────── │ app.js │ │ │ └─────────────┘ │ ├─► CDR (SQLite, WAL) │ ├─► _call_activity dict (last_customer_text, last_rep_text, …) │ │ │ └─► /ws/events fanout ──────────────────────────────────────┘ │ ▼ monitor.html row patch

Four boxes are doing the real work:

  1. The SignalWire Relay runs the SWML script we render — answer, connect the two legs, attach an ai_sidecar verb, and (for any monitored call) attach a tap verb that mirrors audio to a WebSocket URL.
  2. The brian_sidecar service is the FastAPI app that hosts SWML rendering, the /events webhook, the per-call activity table, the WebSocket fanout, and the static UI.
  3. The rep's browser runs the SignalWire SDK and the main copilot UI. It POSTs every utterance it observes to /speaker-event so the backend has a copy.
  4. The supervisor's browser opens the monitor page, subscribes to the event WebSocket, and (optionally) opens a per-call audio WebSocket.

Per-call audio without RTP

The natural way to mirror a SignalWire call somewhere else is RTP — but RTP doesn't traverse browsers, and standing up a TURN server for one listener per call is heavy. The tap verb has a second mode: hand it a WebSocket URL and it pushes μ-law PCMU frames straight to that socket, 8 kHz mono, 160 bytes every 20 ms.

The fiddly part is per-call routing. SWML's variable substitution doesn't fire at the time the tap verb renders — embedding %{call.id} in the URI gets you an empty string. So the backend generates a fresh session_id nonce at SWML render time and bakes it into both the tap URI and a status-callback URL: 

session_id = secrets.token_urlsafe(12)
self._audio_sessions[session_id] = _AudioHub()

tap_uri = ws_base + self.route \
    + f"/ws/audio?session={session_id}&ticket={ticket}"

tap_status_url = self._webhook_url(
    f"/tap-status?session={session_id}")

main_section.append({"tap": {
    "uri": tap_uri,
    "direction": "both",
    "codec": "PCMU",
    "status_url": tap_status_url,
}})

When the relay opens the tap, it also fires /tap-status with the real call.id. That handshake is what tells the backend "session X belongs to call Y" — the rest of the codebase keys off call_id, so this is the bridge.

Playing μ-law in a browser

The supervisor clicks Listen, mints a short-lived ticket, opens /sidecar/ws/audio/listen?session=…&ticket=…, and starts receiving μ-law frames. Three steps to turn those into sound:

  1. Decode each byte through a pre-built 256-entry table to a Float32 sample in the range [-1, 1].
  2. Resample 8 kHz → AudioContext rate (typically 48 kHz) with a linear interpolator. Linear is fine for speech; the energy above 4 kHz that a sharper filter would preserve doesn't exist in the source.
  3. Hand off to an AudioWorklet that owns a 500 ms ring buffer. Worklets run on the audio rendering thread, so they can't stall when the main thread is busy laying out the table.

The ring buffer drops oldest samples on overflow and zero-fills on under-run, which gives a calm degradation when the network is flaky — brief silences instead of glitches.

Real-time push without polling

The 3-second poll is a safety net. For sub-second updates, the monitor subscribes to /ws/events — the same WebSocket the rep's UI uses. The backend fans every sidecar event (turn, transcribe, insight, tool_call, skip, monitor.coaching) out to every connected subscriber. The monitor's onmessage handler patches the in-memory row for the right call_id and re-renders just that row: 

function _patchCall(callId, patch) {
  let c = _calls.find((x) => x.call_id === callId);
  if (!c) {
    c = { call_id: callId, started_at: now(), … };
    _calls.unshift(c);
  }
  Object.assign(c, patch);
  renderTable();
}

If an event arrives for a call we haven't polled yet, a placeholder row appears immediately and the next poll fills in the missing fields. The poll-and-push pair means the table is correct within 3 seconds even if the WebSocket drops, and within ~50 ms when it's connected.

Per-side freshness, fading independently

Each call row tracks two timestamps: last_customer_at and last_rep_at. The customer cell looks at the first one to decide whether to pulse; the rep cell looks at the second. They fade independently — if the customer is talking while the rep is silent, the customer cell pulses red and the rep cell sits dim, and vice versa.

Two pieces make the fade work without flicker:

  • The backend keeps the most-recent non-empty text per side, so a content-less ping (the early warning we sometimes broadcast before the final text is known) won't wipe the cell back to a dash mid-call.
  • The frontend arms a 4.2-second timer on every fresh utterance per side. When the timer fires it bumps the age past the "fresh" threshold and re-renders, so the cell fades even if no further events arrive.

The echo bug that nearly shipped

Symptom: the customer and rep cells flashed nonstop, repeating text that hadn't been spoken in minutes. The dots pulsed in a fast alternating pattern. Audio was fine.

The rep's browser POSTs every utterance to /speaker-event. That handler updates _call_activity and broadcasts a synthetic transcribe.utterance event so the monitor sees it in real time.

The rep's browser also subscribes to /ws/events — the same fanout the monitor uses. When the synthetic event got broadcast, the rep UI saw it, classified it as a transcribe event, and POSTed it back to /speaker-event. Which broadcast it again. Which the rep UI received again. Infinite loop, tight enough to keep both cells permanently "fresh".

The fix is one field. The synthetic broadcast stamps itself "origin": "monitor_relay"; the rep UI skips the back-POST when it sees that marker: 

if (role && state.call?.id && evt.origin !== "monitor_relay") {
  fetch(`${API_BASE}/speaker-event`, { … });
}

Real relay-delivered events don't carry that field, so they still POST. Synthetic ones we re-fanned out are short-circuited. The lesson — when a broadcast bus and an HTTP write path both touch the same state, mark which one is the echo or you'll get one.

Recordings live with SignalWire, not us

The monitor's listen-in audio is for live calls only — once a call ends the WebSocket closes and the μ-law buffer drains. For historical playback, the SWML carries a record_call verb (when SIDECAR_RECORD_CALLS=1) so SignalWire records the bridged call into its cloud recording store. The CDR detail modal retrieves it on demand via SignalWire's LaML-compat recordings endpoint (GET /api/laml/2010-04-01/Accounts/{ProjectId}/Recordings.json?CallSid=…) and plays the mp3 through a backend proxy that injects project basic-auth, so the browser never sees the API token.

There is a native Relay equivalent (GET /api/relay/rest/recordings) and it's even what the agents SDK's RecordingsResource targets — but at the time of writing it has no working call-id filter. ?call_id=…, ?CallSid=…, and ?relay_pstn_leg_id=… are all silently ignored: the endpoint returns the unfiltered page regardless. Combined with the fact that each recording carries only relay_pstn_leg_id (the PSTN-side leg) and not the SWML call_id we get from the webhook, finding "the recording for this call" via the relay path would mean fetching every recording in the project and matching client-side. LaML's ?CallSid=… does it in one round trip, so that's what's wired.

This split — live monitor for the present, CDR + recording for the past — keeps each surface focused. The monitor stays small (a table plus a μ-law decoder); the historical view inherits SignalWire's storage instead of duplicating it locally.

Why a CDR sits underneath all of this

Everything above is volatile — process restart and the _call_activity dict empties. The CDR (a SQLite database with WAL mode on) is the durable record. The monitor's "active calls" query is just SELECT … WHERE ended_at IS NULL against that table, with a stale-sweep that closes any row whose last update is older than 10 minutes. If a container gets rebuilt mid-call the row will eventually seal itself with end_reason='stale' instead of haunting the table forever.

Where the boundaries are

A handful of opinions made this small enough to fit in one page:

  • No new database. The CDR table and an in-memory activity dict are enough; nothing in the monitor needs to survive longer than the call itself, except what the CDR already captures.
  • Browser does the resampling. Shipping μ-law over the wire (instead of decoded PCM) keeps the WS frames at 8 kbps per listener.
  • Push for liveness, poll for truth. The push path is best-effort. The poll is authoritative. Neither has to be perfect because the other is also there.
  • Synthesise events, don't synthesise state. When the rep's UI wants the monitor to know something, it POSTs an event that becomes a broadcast. There's no second pipe for "monitor state" — the fanout is the only message bus.
